# Предложение о независимом доступе к БД

Статус на 14.11.2026 (Asia/Yakutsk): владелец проекта подтвердил согласие преподавателя на SSH-туннель.
Приложение доступно по HTTPS в режиме `preview`; MongoDB и Node.js работают в отдельном runtime.
После автоматического восстановления 13.11.2026 оба дела проверены напрямую в MongoDB и через API:
полный SHA-256 документов совпал со снимком до остановок.

Согласование способа не означает готовность канала: подключение с аккаунта или ограниченного ключа
именно преподавателя ещё не проверено. Выдача ему доступов и доставка сообщения через Moodle REST
не подтверждены; отметка `db-access-approved` на сервере отсутствует. Основной SSH-ключ студента
и ключ автоматического восстановления для доступа преподавателя не передаются.

Подготовлены [самостоятельный деплой и инструкция](helios-deployment.md). Публичный `preview` разрешает
проверку HTTPS без отметки согласования. Он использует ту же БД и Bearer-защиту, не является сдачей
работы и не подтверждает преподавательский доступ. Обычный deploy требует отдельной отметки согласования;
она не заменяет реализацию и проверку ограниченного DB-канала.

После согласования передам API-токен, отдельные данные БД и инструкцию личным сообщением через Moodle REST API. Затем отдельно проверим Ваше подключение. Приложение оставлю доступным на согласованный период проверки. Если такой доступ не подходит, согласую другую площадку до сдачи работы.

## Технические ограничения

- Отдельный приватный корень `~/.node-todo-final`, собственные data/log/run/env. Каталог `~/.moodle-lti-rag` и его MongoDB не используются для данных TODO.
- Настроены loopback-порты: Node `30356`, MongoDB `30357`. После закрытого теста слушатели были остановлены; публичный preview запускает их снова. Текущее состояние проверяется через `helios:status` и `sockstat`.
- В отдельном runtime проверены Node.js 24.21.0 и MongoDB 8.0.29 для FreeBSD 14 amd64. Тест включал настоящие операции с БД, а не только вывод версий.
- MongoDB запускается с authentication. Роль `tasksCrud` содержит только `find`, `insert`, `update`, `remove` для точной пары `{db: "node_todo_final", collection: "tasks"}`. Обычная роль `readWrite` не используется: она шире требуемого доступа.
- Коллекция, валидатор, индексы, пользователь приложения и отдельный пользователь проверяющего инициализированы. Секреты администратора не передаются приложению или преподавателю.
- На общем сервере нельзя полагаться только на bind `127.0.0.1`: локальные пользователи тоже могут обращаться к нему. Авторизация MongoDB обязательна.

## Варианты после согласования

### Собственный аккаунт преподавателя на Helios

Предпочтительный вариант, если у преподавателя есть свой SSH-доступ и сервер разрешает ему forwarding.
Преподаватель использует собственную учётную запись; студенческий пароль, ключ и shell-доступ ему не передаются.
Это обычный туннель под его аккаунтом, а не ограниченный ключ к аккаунту студента. Его работоспособность
нужно проверить отдельно. Локальный порт слушает только `127.0.0.1` на компьютере преподавателя.
Основание: [OpenSSH local forwarding](https://man.openbsd.org/ssh#L),
[настройки разрешений сервера](https://man.openbsd.org/sshd_config#AllowTcpForwarding).

Пример для согласованного теста после запуска сервисов, не команда для выполнения сейчас.
В `TEACHER_HELIOS_LOGIN` нужно задать собственный логин преподавателя, а ключ сервера сверить
с доверенным источником. Если локальный порт занят, выбрать другой и заменить его в обеих командах.

```bash
ssh -p 2222 -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:27018:127.0.0.1:30357 \
  "${TEACHER_HELIOS_LOGIN:?}@helios.cs.ifmo.ru"
```

В другом терминале при открытом туннеле; пароль БД вводится по запросу, не включается в URI:

```bash
mongosh 'mongodb://127.0.0.1:27018/node_todo_final?directConnection=true' \
  --username todo_reviewer --authenticationDatabase node_todo_final --password
```

### Выделенный ограниченный ключ

Преподаватель создаёт отдельную пару SSH-ключей и передаёт только публичный ключ. Для этого ключа задаётся forced command, соединяющий stdin/stdout только с `127.0.0.1:30357`, например `/usr/bin/nc 127.0.0.1 30357`, вместе с опцией `restrict`. На клиенте небольшой проверяемый bridge связывает локальный TCP-порт с `ssh -T`. Для MongoDB используется `directConnection=true`.

Такой режим не использует обычный `ssh -L`: forwarding запрещён, а подключение выполняет фиксированная команда. Нельзя просто добавить `restrict,port-forwarding,permitopen=...` и считать доступ полностью ограниченным: `permitopen` ограничивает `-L`, но сам по себе не ограничивает `-R`.

Перед выдачей доступа нужно проверить на реальном ключе, что shell, произвольные команды, SFTP, local/remote forwarding недоступны, а CRUD нужной коллекции работает. Bridge и запись authorized_keys для этого варианта не входят в текущий пакет. После полученного согласия нужно выбрать вариант подключения и проверить допустимость конфигурации на Helios; преподавательский канал ещё не испытан. После завершения проверки временный ключ и DB-пользователь отзываются.

Основание: [OpenSSH authorized_keys](https://man.openbsd.org/sshd.8#AUTHORIZED_KEYS_FILE_FORMAT), [ограничение MongoDB до коллекции](https://www.mongodb.com/docs/manual/core/collection-level-access-control/). Документация повторно проверена 11.11.2026; конфигурация преподавательского ключа ещё не испытана.

## Последовательность размещения

Предварительно можно явно выполнить `helios:preview` для проверки HTTPS владельцем. Отметка согласования
при этом не создаётся, доступ преподавателя не выдаётся. Это не заменяет следующие шаги сдачи.

1. Согласие на SSH-туннель уже получено. Уточнить собственный аккаунт преподавателя либо выделенный ключ, клиент и период проверки. Не считать студенческий SSH-тест проверкой его доступа.
2. Подготовить выбранный канал. Для выделенного ключа заранее испытать такую же конфигурацию на отдельном тестовом ключе: CRUD разрешён, shell, SFTP, произвольные команды и forwarding запрещены. Приватный ключ преподавателя не запрашивать. Отметку `db-access-approved` создавать только после реального согласования, не для обхода проверки деплоя.
3. Выпустить точный commit через подготовленный deploy, не заменяя БД и конфигурацию. Проверить публичные login, readiness, Bearer-защиту, HTTP-контракт и интерфейс.
4. Передать API-токен и отдельные доступы БД личным сообщением через Moodle REST, подтвердить доставку. Проверить вход преподавателя и повторить API → БД и БД → API через HTTPS и его канал. Создать персональное дело с `runId=manual` через опубликованное приложение, проверить сохранение после рестарта.
5. В форум приложить HTTPS-адрес, README и доступные исходники точного commit либо ZIP без секретов. Поддерживать доступность в период проверки, затем отозвать временный DB-доступ и выделенный ключ, если он использовался.

## Личное сообщение через Moodle REST

Ниже только шаблон, он не выполнялся. `MOODLE_BASE_URL` должен быть точным корнем нужной Moodle, включая `/m`, если установка находится в подпапке. ID преподавателя нужно проверить в её профиле, а не переносить из другого Moodle. Токен Moodle должен разрешать функцию отправки сообщений; это не API-токен нашего приложения.

Подготовить окончательный текст в приватном `.local/moodle-message.txt` с правами `600`, без добавления файла в Git. До деплоя достаточно отправить предложение выше без паролей; действующие доступы передаются отдельным сообщением после проверки.

```bash
curl --fail-with-body --silent --show-error \
  "${MOODLE_BASE_URL%/}/webservice/rest/server.php" \
  --data-urlencode "wstoken=${MOODLE_WS_TOKEN:?}" \
  --data-urlencode 'wsfunction=core_message_send_instant_messages' \
  --data-urlencode 'moodlewsrestformat=json' \
  --data-urlencode "messages[0][touserid]=${TEACHER_ID:?}" \
  --data-urlencode 'messages[0][text]@.local/moodle-message.txt' \
  --data-urlencode 'messages[0][textformat]=2'
```

Не использовать `curl -v` и не публиковать переменные, запрос или ответ: ответ Moodle может содержать исходный текст с секретами. HTTP 200 недостаточно; проверить отсутствие `exception`/`errorcode`, положительный `msgid` и отсутствие `errormessage`. При `msgid=-1` сообщение не доставлено; автоматически повторять запрос без проверки не следует.

Официальные источники: [REST-клиент Moodle](https://docs.moodle.org/dev/Creating_a_web_service_client), [параметры и результат функции](https://github.com/moodle/moodle/blob/MOODLE_405_STABLE/message/externallib.php). Наличие функции и права конкретной учётной записи ещё нужно проверить в используемой учебной Moodle.
