# Публикация TODO на Helios

## Статус и границы

Подготовлен деплой из корня отдельного репозитория `WhoamiTitle/node-todo-final`.
Адрес существующего стенда сохраняется: `https://se.ifmo.ru/~s507353/todo/`.
Перенос исходников не публикует новую версию и не меняет конфигурацию или данные Helios.
До первого выпуска выполнить [план переключения репозитория](standalone-migration.md).

Для сдачи сначала согласовать [предложение о доступе к БД](access-proposal.md). Отдельный режим
`preview` позволяет проверить публичный HTTPS до согласования, не подменяя факт согласия преподавателя.
Не выдавать основной SSH-пароль,
не открывать MongoDB в интернет и не считать HTTP API заменой независимого подключения к БД.
Согласованный канал ещё нужно реализовать и проверить отдельно; скрипты деплоя ключей не добавляют.

## Устройство

```text
HTTPS /~s507353/todo/ -> PHP gateway -> Node.js 127.0.0.1:30356
                                      -> authenticated MongoDB 127.0.0.1:30357

~/.node-todo-final/
  packages/             отдельные архивы FreeBSD
  runtime/              отдельные Node.js, MongoDB, npm и библиотеки
  releases/<commit>/    код, production node_modules, сгенерированные иконки
  current -> releases/<commit>
  config/app.env        токен API, автор, ограниченный DB-пользователь приложения
  config/database.env   администратор и параметры инициализации, не передаются Node-сервису
  config/reviewer.env   отдельный доступ проверяющего
  config/mongod.json    loopback, authentication, отдельный dbPath
  config/db.initialized
  config/db-access-approved
  publication-mode      preview или approved; не заменяет согласование доступа
  data/mongo/           постоянные данные, не входят в релизы
  logs/                 раздельные журналы Node.js и MongoDB
  run/                  PID-файлы и системные блокировки
  incoming/             загруженные архивы

~/public_html/todo/     только index.php, .htaccess и служебная отметка владельца деплоя
```

Порты указаны как кандидаты, перед первым запуском проверить занятость через `sockstat`.
Пользователи общего сервера могут обращаться к loopback, поэтому MongoDB запускается с обязательной
аутентификацией. Процессы и файлы LTI не используются. Шлюз сохраняет Authorization, Content-Type,
JSON, методы, статусы и CORS; `/todo/api/tasks/` преобразуется во внутренний `/api/tasks/`.
У шлюза фиксированный backend, ограничены размеры запросов/ответов и время ожидания.
В `.htaccess` шлюза нельзя задавать `Options`: Helios отклоняет эту директиву с HTTP 500 ещё до PHP.
Локальный Apache-тест запрещает override категории Options, чтобы обнаруживать эту несовместимость.
Публичный каталог содержит только gateway; остальные пути, включая скрытые файлы, обрабатывает приложение.

## Сначала защитить каталог от портфолио

В environment `helios-production` репозитория `WhoamiTitle/web-languages-portfolio` установить:

```text
DEPLOY_PRESERVE_PATHS=mkdocs-deployment-lab,moodle-lti-rag,todo
```

То же значение нужно в локальном `.env` портфолио. Новая версия `deployment-common.sh` добавляет
`todo` и при старом значении переменной, но старые версии скриптов этого не делают. Сначала
опубликовать проверенные изменения защиты портфолио; не запускать старый deploy/rollback со старым
списком исключений после появления `/todo/`. Исключение применяется к upload, backup, activate и rollback.

## Подготовка исходников и локального доступа

Все команды ниже выполняются из корня нового репозитория. Нужны Node.js 24, npm, Git, tar и OpenSSH.

```bash
npm ci --ignore-scripts
npm run check
npm run test:deployment
cp .env.helios.example .env.helios
chmod 600 .env.helios
```

В `.env.helios` указать свой логин, путь к отдельному SSH-ключу и проверенному known_hosts.
`TODO_PACKAGE_CACHE` задаёт каталог уже скачанных `.pkg` на **Helios**, не на локальном компьютере.
Для нашего аккаунта это `/home/studs/s507353/.moodle-lti-rag/packages`: из него только читаются архивы,
копируются в собственные `packages/` и распаковываются в собственный runtime. Это не использование
runtime, конфигурации или БД LTI. Для другого аккаунта нужен свой кеш с тем же набором архивов.
Пароли MongoDB и API-токен сюда не помещаются. Сам файл исключён из Git.
Секреты и данные из старой локальной копии `Documents/node-todo-final` автоматически не переносятся.

После проверки изменений отдельно согласовать commit/push. Сборка релиза отказывается работать
с незакоммиченными изменениями в репозитории. Она использует `git archive` для точного
HEAD, а не копирует рабочий каталог. `.env`, данные, вложенный Git и локальные node_modules не попадают
в архив. Иконки собираются из зафиксированной dev-зависимости; production npm ci выполняется на FreeBSD.

## Первичная настройка сервера

До этих команд проверить допустимость запуска и ресурсы аккаунта. Они не выполняются автоматически
при push и не вызываются workflow публикации.

Это раздел для новой пустой установки. При переносе существующего стенда не выполнять повторную
инициализацию, не создавать новую БД и не менять `config/`, `data/` или runtime.

```bash
npm run helios:prepare
npm run helios:init-db
```

`prepare` создаёт закрытый корень с правами 700, берёт закреплённые пакеты FreeBSD 14 amd64 из
`TODO_PACKAGE_CACHE` или загружает по HTTPS и распаковывает только `/usr/local/*` в собственный runtime.
Системная установка не выполняется. Проверка 10.11.2026 показала HTTP 404 для закреплённых старых URL,
поэтому для первого запуска нужен сохранённый кеш; скрипт не заменяет версии на новые автоматически.
Существующий runtime не обновляется автоматически. Список пакетов находится в
`deploy/helios/freebsd-packages.txt`. До распаковки каждый архив проверяется по
`freebsd-packages.sha256`. Хеши зафиксированы 10.11.2026 с ранее скачанного и проверенного набора
Helios. Это защита от подмены выбранных архивов, но не независимая проверка подписанного каталога FreeBSD.

Конфигурация генерирует случайные секреты и создаёт файлы с правами 600, не выводя значения.
Существующая конфигурация никогда не перезаписывается. Если подготовка прервалась и оставила неполные
runtime/config/release, скрипт требует ручного осмотра, а не удаляет их автоматически.

`init-db` проверяет пустой каталог данных и минимум 1 GiB свободного места на его файловой системе
до запуска `mongod`. При отказе пользователи, коллекция и отметка `db.initialized` не создаются.
Это не заменяет проверку пользовательской квоты; `/tmp` для данных БД не использовать.
Временная MongoDB слушает исключительно Unix-сокет
в закрытом каталоге пользователя, без TCP и доступа других студентов. Создаются администратор, схема,
индексы и два разных пользователя с CRUD только в `node_todo_final.tasks`. После этого временный процесс
штатно завершается. Обычный запуск использует `authorization: enabled` и отключает localhost bypass.
Повторная команда после успешной инициализации ничего не меняет. Непустая БД без отметки успешного
завершения требует разбора, не повторной генерации паролей или удаления данных.

**Только после реального согласования преподавателем** на Helios отметить это решение:

```bash
touch ~/.node-todo-final/config/db-access-approved
chmod 600 ~/.node-todo-final/config/db-access-approved
```

Отметка не реализует и не проверяет SSH-канал. До сдачи отдельно испытать его ограничения и CRUD
из независимого DB-клиента. Не создавать отметку лишь ради прохождения проверки workflow.

## Публичный preview до согласования

После подготовки runtime и инициализации БД выполнить из чистого коммита:

```bash
npm run helios:preview
npm run helios:status
curl -i 'https://se.ifmo.ru/~s507353/todo/healthz/'
```

Команда запускает сервисы и публикует `/todo/`, но **не создаёт** `config/db-access-approved`.
В приватном `publication-mode` записывается `preview`; шлюз возвращает `X-Todo-Mode: preview`
и `X-Robots-Tag: noindex, nofollow`, включая ошибки, API и статические ресурсы.
Запрет индексации не является контролем доступа: страница и `/login/` публичные, все `/api/`
по-прежнему требуют Bearer-токен. Это та же постоянная БД, не песочница с копией данных.
Не публиковать токен, строки подключения и тестовые записи с личными данными.

Проверки выпуска проходят сначала на loopback, затем по HTTPS; публичные контракты дополнительно
проверяют режим и заголовки. Неуспешная первая публикация возвращает закрытое состояние,
неуспешное обновление восстанавливает предыдущий gateway и режим. Рабочий preview остаётся запущенным.
`helios:status` отдельно показывает режим и наличие отметки согласования.

GitHub workflow не поддерживает preview и сохраняет свой gate согласования. Для перехода из preview
к обычной публикации после реального согласования создать отметку выше и выполнить `helios:deploy`.
Без неё обычный deploy завершается отказом. Сам факт публикации не означает приёмку задания;
независимое подключение преподавателя и сдача остаются отдельными шагами.

## GitHub Actions

В новом репозитории **WhoamiTitle/node-todo-final**. Environments, variables и secrets из портфолио
не переносятся автоматически. Настроить их отдельно перед согласованным выпуском; до этого
не запускать deploy. Старые настройки портфолио на этапе подготовки не менять.

1. `Settings -> Environments -> New environment`: создать **helios-todo**.
2. Разрешить деплой только из `main`; включить ручное подтверждение там, где это позволяет тариф.
3. В **Environment variables** добавить:

| Переменная                | Значение                         |
| ------------------------- | -------------------------------- |
| `TODO_DEPLOY_HOST`        | `helios.cs.ifmo.ru`              |
| `TODO_DEPLOY_PORT`        | `2222`                           |
| `TODO_DEPLOY_USER`        | `s507353`                        |
| `TODO_DB_ACCESS_APPROVED` | `true` только после согласования |

4. В **Environment secrets** добавить:

| Secret                   | Содержимое                                                     |
| ------------------------ | -------------------------------------------------------------- |
| `HELIOS_SSH_PRIVATE_KEY` | Полный приватный ключ разрешённого deploy-доступа, с BEGIN/END |
| `HELIOS_KNOWN_HOSTS`     | Проверенные записи ключей сервера для порта 2222               |

Приватный ключ не вставлять в Variables, репозиторий или форум. Fingerprint known_hosts проверить
по доверенному источнику, не доверять одному ssh-keyscan. Предпочтителен отдельный deploy-ключ;
создание и добавление ключа в authorized_keys здесь не автоматизированы.
API-токен, root-пароль MongoDB и доступ преподавателя в GitHub не нужны: они остаются на Helios.

5. После push дождаться workflow **TODO quality**. Он использует Node.js 24, временный MongoDB service,
   HTTP/unit, реальные DB-тесты, PHP gateway, локальные модели activate/rollback и npm audit.
   DB-пароль в YAML является только тестовым паролем одноразового service, не production-секретом.
6. `Actions -> Deploy TODO to Helios -> Run workflow`, ветка `main`, операция `deploy`.

Workflow публикации запускается только вручную. У TODO собственная concurrency group `helios-node-todo`;
GitHub concurrency действует внутри одного репозитория, не между старым и новым. Не запускать
два выпуска одновременно; на сервере операции дополнительно защищены lockf. PHP-портфолио выпускается отдельно.
Для ручного локального выпуска: `npm run helios:deploy`.

## Как проходит обновление и откат

Архив поступает под уникальным временным именем. На сервере под блокировкой устанавливаются зависимости
`npm ci --omit=dev --ignore-scripts`, затем проверяется отметка инициализации. Обычный deploy дополнительно
требует согласования DB-доступа; явно выбранный preview не меняет эту отметку.
Останавливается только Node.js; существующая MongoDB и её файлы остаются на месте. Переключается `current`,
запускаются/проверяются supervisor и приложение. После локальных HTTP-проверок публикуется gateway,
затем те же контракты проверяются по публичному HTTPS.

Проверки включают login, readiness, отсутствие доступа без Bearer, author, CORS, HTML/JS и CRUD временного
дела с уникальным `runId=deploy_*`. Успешная проверка удаляет только своё дело. При сетевой аварии тестовое
дело может остаться; это не основание очищать коллекцию. Реальное подключение преподавателя проверяется отдельно.

При ошибке активации откат возвращает код, шлюз и прежние значения `deployed-release`, `previous-release`
и `publication-mode`. Файлы метаданных, которых до выпуска не было, после отката не остаются.
База и секреты не откатываются. Первый неудачный выпуск останавливает свои сервисы и убирает свой публичный gateway,
сохраняя БД и релиз для разбора. Если процесс не останавливается штатно, выпуск прекращается без SIGKILL.

Ручной откат к уже установленному полному SHA:

```bash
npm run helios:rollback -- ПОЛНЫЙ_SHA_КОММИТА
```

Локальный rollback сохраняет текущий режим публикации, поэтому preview не становится approved при откате.
Целевой релиз должен поддерживать режимы публикации: релизы до добавления preview отвергают новый
формат команды до любых изменений. Для preview проверяйте локальный rollback, не workflow с gate согласования.
Для согласованного выпуска доступен и workflow, операция `rollback`, поле `release` с полным SHA. Старый код должен быть совместим
с текущей схемой: никаких автоматических миграций/отката данных эти скрипты не выполняют. Релизы и журналы
пока не удаляются автоматически; следить за квотой, выполнять отдельный backup БД и согласованную ротацию.

## Эксплуатация и приёмка

```bash
npm run helios:status
npm run helios:stop
npm run helios:start
```

Node и MongoDB работают в foreground под разными FreeBSD daemon с задержкой повторного запуска 5 секунд.
PID проверяется по UID и команде. Остановка сначала завершает supervisor Node и приложение, затем MongoDB.
Повторный start не создаёт дубликаты. Повреждённый PID или посторонний процесс означают отказ с диагностикой.
Для сбоя посмотреть `~/.node-todo-final/logs/node-supervisor.log`, `mongo-supervisor.log`, `mongo.log`.
Журналы приватные; не публиковать их целиком без проверки на чувствительные данные.

Cron на Helios не используется. После перезагрузки Helios или завершения самого supervisor запуск ручной,
если отдельно не включено [внешнее автовосстановление](helios-recovery.md). Оно выключено по умолчанию,
требует отдельного ограниченного ключа и разрешения на автозапуск. Остановку всех процессов администрацией
supervisor не предотвращает; намеренную политику сервера нельзя обходить восстановлением без согласования.

После выпуска проверить `/todo/login/`, `/todo/healthz/`, интерфейс и независимое изменение той же коллекции.
Создать персональное manual-дело в опубликованном приложении. В форум дать URL и ссылку
`https://github.com/WhoamiTitle/node-todo-final/tree/<commit>` с SHA из
`~/.node-todo-final/current/REVISION` после завершения деплоя. Он должен совпадать с `deployed-release`.
API/DB-доступ передавать отдельно личным сообщением Moodle,
только после проверки адресата. Тестовый успех и наличие CI YAML не подтверждают выполнение этих действий.

Официальные источники: [FreeBSD daemon](https://man.freebsd.org/cgi/man.cgi?query=daemon&sektion=8&manpath=FreeBSD+14.3-RELEASE),
[FreeBSD lockf](https://man.freebsd.org/cgi/man.cgi?query=lockf&sektion=1&manpath=FreeBSD+14.3-RELEASE),
[MongoDB configuration](https://www.mongodb.com/docs/v8.0/reference/configuration-options/),
[collection-level privileges](https://www.mongodb.com/docs/manual/core/collection-level-access-control/).
