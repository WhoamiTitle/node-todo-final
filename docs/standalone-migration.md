## Адаптация исходников

- `package.json`, lock-файл, README, слои и тесты находятся в корне самостоятельного репозитория.
- `scripts/package-release.sh` требует чистый commit и корень репозитория, использует `git archive HEAD`
  с прежним ограниченным списком release-файлов. Иконки собираются из закреплённых зависимостей.
- Apache-регрессия использует `tests/fixtures/portfolio.htaccess`, снимок родительских правил
  из того же исходного commit. Тест больше не читает соседний checkout. При изменении live-правил
  портфолио обновить этот fixture отдельным проверенным изменением.
- Три workflow работают с корнем, а не подпапкой монорепозитория. Quality запускается при push/PR;
  deploy только вручную. Recovery не получает права запуска, пока repository variable не равна `true`.

Сравнение 74 файлов индекса с исходным commit подтвердило 62 полностью неизменённых файла;

## Совместимость CI runner и MongoDB

Первый GitHub run выявил ошибку кавычек в унаследованном `--health-cmd`; исправлено так,
чтобы `--eval` был аргументом mongosh, а не Docker. Следующий run создал контейнер, но MongoDB
отказалась запускаться на ядре runner: несовместимость TCMalloc с Linux 6.19–7.0.13
[подтверждена MongoDB](https://www.mongodb.com/docs/manual/release-notes/8.0/).

На 14.11.2026 GitHub описывает ядро 7.0.0 для Ubuntu 24.04, поэтому простая замена latest
на 24.04 не устраняет проблему. Только quality job временно использует `ubuntu-22.04`,
для которого указан Linux 6.8. MongoDB image, зависимости приложения и FreeBSD runtime не меняются.
Deploy и recovery не выполняют MongoDB в контейнере runner и сохраняют прежние labels.

Владелец проекта должен проверить совместимую новую комбинацию runner/kernel/MongoDB и убрать этот
пин до [вывода Ubuntu 22.04 из поддержки 17.04.2027](https://github.com/actions/runner-images/issues/14254),
раньше brownout-периодов марта. Нельзя отключать MongoDB kernel-check или выдавать локальный успех
за прохождение GitHub. Текущие образы: [Ubuntu 22.04](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2204-Readme.md),
[Ubuntu 24.04](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md).

## Подготовка GitHub без переключения

1. Отправить проверенный commit в `main`, дождаться **TODO quality** нового репозитория.
2. Создать environment `helios-todo`, разрешённая ветка `main`. По
   [инструкции деплоя](helios-deployment.md) вручную добавить три `TODO_DEPLOY_*` variables,
   gate `TODO_DB_ACCESS_APPROVED` только при действительном согласовании и два SSH secrets.
3. Создать environment `helios-todo-recovery`, разрешённая ветка `main`, без ручного ожидания
   для будущего расписания. Добавить `TODO_DEPLOY_*`, отдельный ограниченный
   `TODO_RECOVERY_SSH_PRIVATE_KEY` и проверенный `HELIOS_KNOWN_HOSTS`.
4. В **Repository variables** нового репозитория установить `TODO_RECOVERY_ENABLED=false`.
   Отсутствующая переменная также не включает scheduled job. Старое значение в портфолио не менять.
5. Запустить новый workflow вручную в режиме `check`: он проверяет только HTTPS без SSH.
   Такой успех не подтверждает deploy-доступ или способность восстановить остановленный сервис.

Секреты не хранятся в Git и не извлекаются из старых Actions. API-токен, MongoDB URI и пароли
не требуются workflows. Приватные значения добавляются владельцем только в Secrets.
Recovery-ключ не заменяет deploy-ключ или канал независимого DB-доступа преподавателя.

## Согласованный выпуск и recovery cutover

1. Сверить активный релиз и режим на Helios, сохранить снимок всех полей учебных дел через
   независимого DB-клиента, подготовить возврат кода. Не запускать `prepare` или `init-db` повторно.
2. В отдельное согласованное окно выпустить новый commit из нового репозитория. Сохранять
   существующий режим: для preview использовать `npm run helios:preview`; workflow deploy
   требует согласования и не является обходом этого gate.
3. Проверить локальную и публичную readiness, login, авторизацию и CRUD. Сравнить сохранённые
   дела полностью, не только количество. Доставку DB-доступа и подключение преподавателя проверить отдельно.
4. Пока новое recovery выключено, проверить его ограниченный SSH-ключ на здоровом стенде:
   shell, SFTP и forwarding запрещены. Не останавливать рабочую БД ради первого теста ключа.
5. После успешной проверки выключить `TODO_RECOVERY_ENABLED` в портфолио, дождаться завершения
   старых monitor jobs и включить его в новом репозитории. Никогда не держать две автоматики включёнными.
   GitHub concurrency ограничена репозиторием; серверный `deployment.guard` остаётся общей защитой.
6. В согласованное окно проверить настоящий `schedule`-запуск и сохранность данных после
   восстановления. Ручной `check` и наличие YAML не доказывают автоматическое восстановление.
7. Только после выпуска обновить ZIP, `SUBMISSION.json`, README и сообщение форума точным новым SHA
   из `REVISION` и `deployed-release`. Не выдавать commit исходников за уже опубликованную версию.

## Остановка перехода и возврат

До первого выпуска можно остановиться после push: прежний стенд и его расписание продолжают работать.
При сбое нового релиза вернуть ранее установленный код штатным rollback, не восстанавливать старые
данные поверх новых дел. Параметры БД, SSH-регистрации и секреты при переносе не меняются.
При отказе новой автоматики сначала выключить её и дождаться завершения job, затем вернуть старую.
Сначала восстановить один подтверждённый источник управления, не включать обе автоматики одновременно.

Удаление дубликата исходников и TODO workflows из портфолио является отдельным шагом после
подтверждённых нового релиза, расписания и сдачи. При удалении сохранить защиту `/todo/`
в upload/backup/rollback портфолио, а карточку заменить ссылкой на новый репозиторий и действующее приложение.
